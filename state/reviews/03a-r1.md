## MAJOR-2 — PATCH şemaları uygulanamayan null'ı kabul edip 500 veriyor

Kaynaklar: `backend/ffcore/api/schemas.py:123` (`UserUpdate`), `:153` (`ProjectUpdate`), `:272` (`ProviderUpdate`), `:417` (`ModelUpdate`); ilgili router'lardaki `model_dump(exclude_unset=True)` + atama/yardımcı çağrıları.

Omission için kullanılan `T | None` alanlar explicit null'ı da kabul ediyor; ama router bunu non-null DB alanına atıyor veya dict bekleyen koda iletiyor. Gerçek uygulama/TestClient + benzersiz fixture DB'de dört ayrı istek doğrulandı:

| İstek | Gerçek sonuç |
|---|---|
| `PATCH /projects/{id}` → `{"name": null}` | **500**, OpenAI hata gövdesi yok |
| `PATCH /users/{id}` → `{"is_active": null}` | **500**, OpenAI hata gövdesi yok |
| `PATCH /providers/{id}` → `{"config": null}` | **500**, OpenAI hata gövdesi yok |
| `PATCH /projects/{id}/models/{id}` → `{"category": null}` | **500**, OpenAI hata gövdesi yok |
| Pozitif kontrol: proje `{"description": null}` | **200**, gerçekten nullable alan |

Sonuç, yalnızca Python şemasına bakılarak çıkarılmadı. DB/Pydantic/TypeError yoluna göre iç hata değişse de istemci hepsinde 500 aldı; asıl sorun field kontratının DB ve endpoint davranışıyla tutarsızlığı.

Beklenen: atlanabilir alan ile null kabul eden alanı ayır. Non-null alanların explicit null'ı anlaşılır İngilizce OpenAI biçimli **422** olmalı; gerçekten temizlenebilir description/reasoning gibi alanlar null kabul etmeli. Omitted alanlar korunmalı, null sessizce no-op'a çevrilmemeli. İlgili PATCH ailelerini parametrik negatiflerle kapsa. OpenAPI taslağındaki nullable düzeltmesini koordinatöre bildirerek şema/sapma testini güncelle; mevcut taslağın null reklamı sessizce bırakılmamalı.
